# E2E

Validate a UI feature end-to-end as cheaply as possible: **the script is the tester, the agent is the exception.** Input is the test case `spec-design` wrote (`artefacts/{sprint}/e2e_{feature}.md`) — missing → ask the user (write one now / skip e2e / verify manually).

**Never end a turn on a run you didn't watch.** Every build, test and driver invocation runs in the foreground and is waited out; where a tool forces it into the background, poll it to exit and read its output before reporting anything. A backgrounded run handed back as a result is a verdict nobody saw — this binds the e2e subagent above all, whose whole output is that verdict.

A red step is a **product bug** → back to implementation (`dynamic-workflow` step 2); red from a selector, a wait or a fixture is a **script bug** → fix the script, never the product.

1. **Automation already runnable?** — run it first, before any delegation: one command, its invocation in `docs/dev.md`. Not just this feature's script: the **flow index** (step 6) names the persistent flows and the area each guards — run those the change touches. The whole suite in one pass is `close-sprint`'s job, not this stage's. Green → step 7, the stage is done. Red → triage per the rule above, except red **before this run touched anything**: that is a pre-existing defect, not this run's problem — ticket it and carry on with the case at hand.
2. **Driver** — **the project's domain owns this choice**: take the one its recipe / testing skill names rather than picking by what happens to be installed. No domain → the framework already in the project; none installable → every step is an agent step. Four rules hold whatever the driver: a **plain-text reporter on stdout is your only input** (never open an HTML report), with the build tool silenced to it — the run's own step report is the whole input, never the build log · **read the running app for a selector, never its source** — every UI stack has a tree dump (accessibility tree, DOM, layout dump); reconstructing a screen from its components plus its string resources costs far more and gets the computed result wrong, and anything ambiguous in that tree wants a test id in the product code, not a cleverer match · a **screenshot only where text can't decide** · **every artifact into `test-dump/`**. The first run configures the driver once and **writes the exact invocation into `docs/dev.md`** — obligatory, and not memory's job: the next run is usually a subagent, which reads the repo and may never see project memory. **The first case's helpers are the project's harness**: a driver is the case's own steps plus the vocabulary for driving that project's screens (open this, tap that, read that value back), and the second case inherits that vocabulary instead of re-deriving it — extract it into one shared base, in whatever form the framework wants (base class, fixture, page object). Re-deriving it is this stage's single largest cost, and it is paid on every run.
3. **Classify each test-case step** `auto` (default) or `agent`. `agent` only for what no assertion can reach: another app, a system dialog, notification, camera, store flow, physical device · a qualitative judgement (does it *look* right, does it feel janky).
4. **Grow the script, one step at a time** — append a step, rerun it whole from the top, read stdout. Never deliberate over whether scripting is worth it: red → fix → rerun is the normal path, free by script and full price by agent, so it pays for itself inside this run.
5. **Agent steps** — drive through the project's MCP server if one is present, otherwise write the user the exact steps and take their result.
6. **Persist or discard** — the script always gets written; only its home is a decision: **persistent** (the flow stays in the product) → the project's test tree, committed, wired into the suite · **temporary** → `test-dump/`, dies with the sprint. A persistent one is **folded into the nearest existing flow, never parked beside it** — overlapping an existing scenario means extending it; only a genuinely new flow becomes a new script. Then update the **flow index** `test/e2e/FLOWS.md` (or the test tree's equivalent path): one line per persistent flow — flow · script · what it asserts · the product area it guards. It is created on the first persist and pointed at from `docs/dev.md` beside the invocation; it is what keeps the suite few and non-overlapping instead of one dead protocol per sprint.
7. **Report & board** — write `artefacts/{sprint}/e2e-report_{feature}.md` from `templates/e2e-report.md`. Green and verified → flip the ticket to `done` on the sprint board; one the user still has to eyeball stays at `to test`.
